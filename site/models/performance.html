Performance: the UI-thread budget

Spec §16: no UI-thread work over 100 ms. Measured with scripts/measure_ui.py (QT_QPA_PLATFORM=offscreen python scripts/measure_ui.py --json out/ui-timings.json) on 2026-11-06: Linux x86_64, AMD Ryzen 9 9900X, Python 3.14.4, PyQt6 6.12.0, NumPy 2.5.4, MuJoCo 3.17.0. The SO-100 sample has 60 682 visual triangles, the UR5e + 2F-85 sample 193 113. Figures are the median of five runs with the largest in brackets; a single figure is one run.

How it is measured. Each handler a user triggers is timed on the UI thread directly. An event-loop watchdog (a 5 ms timer) also records the longest stall while the events that follow each step are processed, so a slow handler the list does not name still shows. Studies and Camera view images run on worker threads and are listed as "worker". Offscreen, the 3D view falls back to the QPainter renderer; its frame is excluded from the UI handlers' figures and listed on its own. The shader renderer's frame (what a desktop pays) is measured headless through EGL on the integrated AMD GPU (radeonsi), the same context the self-test makes.

What was changed to meet it (Phase 2 integration)

Before these changes the shader renderer's frame after a joint change took 108 ms (SO-100) and 385 ms (UR5e):

  • Smooth normals once per model. The renderer merged every corner by position (np.unique over 580 000 corners of the UR5e, 256 ms) at every pose. The scene now computes them once per robot model in each link's own frame (render_gl.vertex_normals(..., group=link)) and rotates them with the links at each q (RobotModel.pose_vectors), handing them to the renderer as MeshDraw.vnormals. Merging in link frames is also steadier: coinciding vertices of two links are no longer smoothed together, and the shading no longer changes as the arm moves.
  • Posing by link. RobotModel.posed_triangles used a 3 × 3 product per triangle (einsum, 33 ms on the UR5e); it now does one matrix product per run of a link's triangles (12 ms, the same numbers to the last bit).
  • Upload. The mesh bounds were an axis-0 reduction of an (N, 3) array (20 ms); per column they take 1 ms. An all-opaque mesh is no longer copied to reorder it.

No UI-thread step is over 100 ms. The largest are on the dexhand sample (30 joints, about 4 900 pad triangles): its Apply 60.7 ms and the events after it 67.3 ms, and its Camera view overlay 53.2 ms worst. Building and showing the main window (once) takes 0.82 s on the UR5e sample and 0.41 s on the dexhand sample, with fourteen pages built at start (0.31 s in Phase 2). With the full test suite running on the same machine one run measured the brackets page's Apply at 146 ms (39 ms idle; profiled alone 46–64 ms, most of it the Sensors and Policies pages rebuilding their editors on the edit), so a loaded machine can push the heavier Apply steps past the budget.

Known limits

  • The QPainter fallback, used only where OpenGL is missing, draws every triangle from Python: 0.16 s per frame for the SO-100 and 0.59 s for the UR5e. A decimated mesh for that path (core/scenegeom.decimate) is the fix; not done.
  • The shader renderer still poses and uploads the whole mesh at each joint change (68 ms median on the UR5e on an integrated GPU, 96 ms at worst). Uploading each link's mesh once and passing the link transforms as uniforms would remove both; that is also what Phase 3's batched occlusion wants (see Occlusion: articulated cube maps and exact ray casting).
  • Measured on one machine; the GL figures are an integrated GPU's. The on-screen QOpenGLWidget path has not been timed on a desktop session.
